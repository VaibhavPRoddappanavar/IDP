System Architecture — Hardware Abstraction and Telemetry Layer                          | Revised hardware abstraction and telemetry description | Replaced the GPU/VRAM/NVML-based description with the actual Raspberry Pi 5 implementation. The HAL now describes CPU utilization, RAM utilization, core temperature, smoothed FPS, and per-frame latency as the five state variables, with asynchronous 2 Hz telemetry sampling through a dedicated background thread and thread-safe in-memory state access. | **Response to Reviewer:** We thank the reviewer for this important question. We note that the original figure contained an error: the HAL does **not** use `ctypes` or a C shared library. It uses Python's `psutil`, which internally reads kernel pseudo-files (`/proc/stat`, `/proc/meminfo`, `/sys/class/thermal/thermal_zone0/temp`) with its own low-latency bindings. We have corrected the figure accordingly. Regarding the GIL concern: the design deliberately avoids GIL contention because the HAL thread is I/O-bound rather than CPU-bound; `psutil` reads kernel pseudo-files and the HAL polls only every 500 ms. The controller forward pass is also negligible, with the lightweight `ContinuousActor` MLP (5→128→128→2) completing in under 1 ms on the Raspberry Pi 5 and executing synchronously on the main thread. The system is designed as a soft real-time system rather than a hard real-time system, and the 2 Hz telemetry rate is sufficient because the relevant thermal dynamics evolve over a much slower timescale. A C++/TensorRT implementation could reduce per-frame inference overhead but would not change the effective control-loop bandwidth, whose adaptation is governed by thermal dynamics rather than telemetry latency. Python was retained for portability and rapid iteration on the Raspberry Pi platform. | Change expected by reviewer<br /><br />The system architecture (Figure 1) relies heavily on Python, ctypes, and OpenCV running in background threads. Python's Global Interpreter Lock (GIL) is known to cause stuttering and unpredictable latency spikes in multi-threaded real-time computer vision pipelines. The authors must provide a rigorous latency profiling of the Python overhead, or explain why a lower-level implementation (e.g., C++ with TensorRT native threads) was not utilized to guarantee strict real-time execution. |
