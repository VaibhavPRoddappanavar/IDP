| 6   | III. The HAL now describes CPU utilization, RAM utilization, core temperature, smoothed FPS, and per-frame latency as the five state variables, with asynchronous 2 Hz telemetry sampling through a dedicated background thread and thread-safe in-memory state access.                                                                                                                                                                                                                      | **Response to Reviewer:** We thank the reviewer for this important question. We note that the original figure contained an error: the HAL does **not** use `ctypes` or a C shared library. It uses Python's `psutil`, which internally reads kernel pseudo-files (`/proc/stat`, `/proc/meminfo`, `/sys/class/thermal/thermal_zone0/temp`) with its own low-latency bindings. We have corrected the figure accordingly. Regarding the GIL concern: the design deliberately avoids GIL contention because the HAL thread is I/O-bound rather than CPU-bound; `psutil` reads kernel pseudo-files and the HAL polls only every 500 ms. The controller forward pass is also negligible, with the lightweight `ContinuousActor` MLP (5→128→128→2) completing in under 1 ms on the Raspberry Pi 5 and executing synchronously on the main thread. The system is designed as a soft real-time system rather than a hard real-time system, and the 2 Hz telemetry rate is sufficient because the relevant thermal dynamics evolve over a much slower timescale. A C++/TensorRT implementation could reduce per-frame inference overhead but would not change the effective control-loop bandwidth, whose adaptation is governed by thermal dynamics rather than telemetry latency. Python was retained for portability and rapid iteration on the Raspberry Pi platform. | Change expected by reviewer |

Added a new Discussion subsection explaining why the system is intentionally connectivity-independent and why edge-cloud offloading was not used, while proposing a hybrid future architecture.                                                                                              | **Response to Reviewer:** We thank the reviewer for raising this important concern. First, the proposed system targets passive road surface monitoring for infrastructure maintenance—a soft real-time application—and not safety-critical ADAS or autonomous driving, for which hard real-time redundant sensor fusion would be mandatory. In this context, a temporary reduction in detection frequency during thermal stress does not create a safety hazard; rather, it prevents total pipeline failure. Second, the static baseline in Phase 0 already sustains a frame-drop rate exceeding 87%. The adaptive frame-skipping mechanism under reduced resolution actually processes a higher effective throughput than the unmodified 640x640 pipeline. Regarding edge-cloud offloading: the system is explicitly designed to be connectivity-independent, as dashboard camera deployments frequently operate in areas with intermittent or absent cellular coverage. Offloading would introduce an additional communication path whose latency and availability depend on network conditions, negating the determinism of a fully local pipeline. However, integrating the proposed local controller with deterministic task offloading represents a powerful hybrid architecture for environments with guaranteed connectivity.                           | Change expected by reviewer |
